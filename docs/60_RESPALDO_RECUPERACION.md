# E1-01 / E1-02 — Respaldo y recuperación (candidato)
Fecha: 25-11-2026. Política aprobada: diario, 30 días, costo adicional inicial cero. Estado: código candidato; NO hay respaldo real activado ni restauración certificada.

## Diseño y límites
El ejecutor ops/backup/backup.mjs se ejecuta en un equipo privado (p. ej. PC Windows del propietario), no en GitHub Actions público ni Vercel. Solo guarda en destino externo un archivo tar.gz.age cifrado con age (destinatario público X25519). El equipo de respaldo no necesita la identidad privada de descifrado. Staging temporal fuera de Git, fuera del directorio sincronizado y sobre volumen cifrado, permisos exclusivos al usuario de tarea. La eliminación de archivos temporales no garantiza borrado físico; cifrado de disco es obligatorio. No subir dumps, manifiestos, credenciales ni claves a GitHub o chats.
Incluye roles, esquema, datos (incluido Auth y metadata de Storage según CLI), historial de migraciones, todos los buckets y objetos físicos S3, manifiesto de tamaño/SHA-256/clave original/tipo/metadata. Los nombres físicos son hashes para evitar rutas inseguras. Comprueba inventario S3 antes/después y descarga condicionada a ETag. Fallo en cualquier paso previo a la publicación conserva respaldos anteriores. Retención de 30 días en destino después de cifrar una nueva copia. El mecanismo no es PITR ni una instantánea transaccional conjunta entre PostgreSQL y Storage: ejecutar en ventana sin operaciones ni migraciones. Un cambio DB concurrente entre dumps puede generar inconsistencia. No asumir recuperación completa hasta ensayo. Configuración de Auth/SMTP, claves, integraciones, settings, cron y políticas personalizadas en esquemas gestionados requieren reconstrucción/verificación aparte con migraciones y configuración documentada; sesiones y tokens anteriores deben revisarse/revocarse en recuperación.
Supabase consultado en solo lectura: 3 buckets privados, 12 objetos, 1.560.835 bytes informados por metadata. El volumen y egreso reales deben medirse: cuota gratuita y espacio de destino pueden crecer. No contratar servicios sin autorización.

## Activación (propietario o técnico autorizado, NO en producción web)
1. Equipo privado con Node 22, Supabase CLI v3 (verificar db dump --help y --db-url), Docker funcional, AWS CLI v2, tar y age/age-keygen instalados. Revisar versiones y registrar las efectivamente ensayadas. No instalar paquetes de fuentes no oficiales.
2. Generar identidad mediante age-keygen -o RUTA_PRIVADA/identity.txt. Guardar identidad en dos ubicaciones privadas seguras, separadas de los respaldos; anotar destinatario público age1... . La pérdida de identidad impide restaurar. NO usar la clave privada en configuración del ejecutor.
3. Obtener del panel Supabase Connect la conexión Direct o Session pooler puerto 5432; agregar sslmode=verify-full si CA disponible, como mínimo sslmode=require. Nunca usar transaction pooler 6543. Codificar caracteres especiales de contraseña en URI. El CLI recibe URI como argumento: solo ejecutar bajo cuenta dedicada/privada; puede ser visible a procesos privilegiados. No usar --debug ni volcar entornos. Si la contraseña se compartió en chats, rotarla con procedimiento coordinado; no modificarla sin autorización.
4. Desde Storage > Configuration, verificar S3 y generar credenciales dedicadas al respaldo, que tienen acceso amplio a los objetos. Configurar perfil AWS exclusivo local mediante aws configure --profile evalia-backup, región y addressing_style=path (aws configure set s3.addressing_style path --profile evalia-backup). No compartir credenciales, restringir ACL de archivos locales. La ejecución solo usa list/get, no muta Storage. No activar S3 ni generar credenciales desde CI.
5. Crear directorio privado de staging cifrado y directorio de destino externo, preferentemente disco separado o carpeta privada de almacenamiento sincronizado (solo ciphertext). Confirmar espacio y cuota para 30 copias. No colocar staging bajo destino ni dentro del repo.
6. Crear archivo local de entorno fuera del repo, ACL privada. Ejemplo sin valores reales:
EVALIA_BACKUP_PROJECT=referencia_proyecto
EVALIA_BACKUP_DB_URL="postgresql://postgres.REFERENCIA:CLAVE@HOST.pooler.supabase.com:5432/postgres?sslmode=require"
EVALIA_BACKUP_S3_ENDPOINT=https://REFERENCIA.storage.supabase.co/storage/v1/s3
EVALIA_BACKUP_S3_REGION=region_del_panel
EVALIA_BACKUP_S3_PROFILE=evalia-backup
EVALIA_BACKUP_RECIPIENT=age1...
EVALIA_BACKUP_DEST="D:/EvaliaCopias"
EVALIA_BACKUP_STAGE="C:/VolumenCifrado/EvaliaTemporal"
7. Desde copia de la rama aprobada para ensayo: node --env-file="RUTA_PRIVADA/backup.env" ops/backup/backup.mjs . No guardar salida de dumps ni de AWS. La ejecución devuelve código distinto de cero si falla. Confirmar archivo .age en destino y, si sincroniza, comprobar que está disponible remotamente. No ejecutar durante cambios de negocio.
8. Solo tras ensayo completo: Programador de tareas Windows, disparador diario en horario de baja actividad (propuesto 03:00 Bolivia, ajustable), ejecutar node.exe con argumentos del paso 7 y directorio inicial de checkout. Ejecutar con cuenta privada y activar "iniciar lo antes posible si se omitió la tarea", reintento tras fallo y no iniciar instancia nueva si hay otra. Docker y volumen cifrado deben estar accesibles a esa cuenta. Si PC apagado no existe garantía diaria; revisar última ejecución y antigüedad del archivo cada día, alertar si >24h. No confundir tarea registrada con respaldo comprobado. Si no hay equipo disponible, evaluar runner privado y destino privado con cuota sin costo adicional. No usar artefactos de repositorio público.
9. Si queda bloqueo .evalia-backup.lock por apagado abrupto, comprobar que no hay tarea activa, borrar manualmente solo ese bloqueo y staging residual seguro. .partial no se considera copia válida; eliminar después de confirmar ausencia de proceso. Si se sincronizan archivos, comprobar subida y retención del proveedor (papelera/versiones aparte).

## Ensayo de recuperación E1-02 (no ejecutar contra producción)
A. Copiar el archivo .age al staging aislado, recuperar identidad privada y descifrar: age -d -i RUTA_PRIVADA/identity.txt -o RUTA_TEMP/payload.tar.gz RUTA_ARCHIVO.age. Inspeccionar listado tar -tzf y extraer únicamente copia propia autenticada, en directorio vacío privado. Ejecutar node ops/backup/verify.mjs RUTA_EXTRAIDA: exige cinco dumps, buckets esperados, coincidencia de inventario y SHA-256 de cada archivo. No copiar ni publicar datos descifrados.
B. Preparar Supabase local aislado NUEVO (workdir temporal, sin conexión a remoto, sin seed comercial, sin SMTP real, no ejecutar migraciones V1 encima del esquema restaurado). Verificar URL de destino loopback y puerto reportado por CLI; nunca usar URI del origen. Aplicar roles.sql, schema.sql, SET session_replication_role = replica y data.sql mediante psql --single-transaction --variable ON_ERROR_STOP=1 siguiendo guía oficial. Migración histórica se restaura por separado tras revisar esquema existente. Si errores, detener, no omitir asserts ni desactivar restricciones definitivamente. Revisar permisos, políticas y triggers personalizados en auth/storage con migraciones del repo; recuperar cron de reserva solo según contrato histórico, no ejecutarlo durante prueba. No aplicar toda la cadena de migraciones dos veces.
C. Recrear/revisar configuración de buckets privados y subir bytes por API de Storage/S3 del entorno local respetando bucket, key y MIME del manifiesto; si la metadata restaurada ya existe, ensayar reemplazo mediante API, nunca manipular storage.objects para simular bytes. Conservar originales y contrastar metadata relevante, descargar nuevamente cada objeto y verificar SHA-256. No usar credenciales de producción para subir.
D. Comparar conteos y relaciones de modelos, clientes, pedidos y líneas, pagos aprobados, stock/compromisos, perfiles, archivos, historial, RLS y grants con el snapshot. Comprobar login de cuenta de prueba en aislado, denegación anon/operador no permitido, pedido, pago, entrega, portal/QR/impresión. Desactivar envío de correo real, no reenviar enlaces previos ni permitir que el entorno local contacte producción. Revisar reconfiguración de Vercel/Auth/SMTP e invalidación de sesiones y enlaces si incidente real.
E. Registrar fecha, versiones, duración real, tamaño, conteos agregados y resultado sin datos personales ni secretos; eliminar staging del ensayo. Restauración certificada solo cuando toda la matriz supera verificación. Prueba de integridad sola NO equivale a recuperación. Si se necesita restore real, autorización independiente, respaldo previo de lo que quede, ventana de mantenimiento y destino verificado.
